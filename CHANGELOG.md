# Change Log

All notable changes to the "DMDB" extension will be documented in this file.

## [v1.0.0] - 2025-01-07

- Initial release

### Added

- Laravel parser from migrations
- Mermaid viewer
- Json viewer

### Known issues
- Many to Many relations are not supported and relations tables appear as empty tables.
- Diagrams with the relationships do not go all the way to the top.

## [v1.1.0] - 2025-03-16

### Added
- Symfony parser from entities
- Symfony framework now supported
- Setting to change the framework directory's path

### Fixed
- Mermaid viewer no longer duplicates tables
- Diagrams with the relationships now go all the way to the top

### Known issues
- No issues known at this time, feel free to report any!


## [v1.1.1] - 2025-06-23

### Added
- Json viewer now supports commited changes

### Fixed
- Mermaid viewer now correctly handles tables with no relationships
- Symfony parser now correctly handles fields with Timestamp type (e.g., `created_at`, `updated_at`)
- Increased font size in Mermaid viewer for better readability

### Known issues
- No issues known at this time, feel free to report any!

## [v1.1.2] - 2026-10-17

Bug fixes and stabilization release.

### Fixed

**Laravel parser**
- Only `up()` is read: `down()` methods (with the `down(): void` stub of Laravel 9+) no longer undo the changes of `Schema::table` migrations
- `id()`, `timestamps()`, `softDeletes()`, `rememberToken()`, `morphs()` and the other helpers now create their real columns
- Foreign keys declared with `foreignId()->constrained()`, `foreignIdFor()`, `foreignUuid()`, `foreignUlid()` and multi-line or reordered `foreign()->references()->on()` chains are now drawn
- `->change()`, `renameColumn()`, `dropColumn()` (also with arrays), `dropForeign()`, `Schema::rename()`, `Schema::drop()` and `dropIfExists()` are now applied, and relations follow renamed or dropped columns and tables
- Double-quoted names, comments, nested closures, any closure signature, `Schema::connection()` and multi-line definitions are now handled
- `index()`, `unique()`, `foreign()` and the drop commands no longer create fake columns
- The `DrawMeDatabase.frameworkPath` setting is now used for Laravel projects too

**Symfony parser**
- `ManyToOne` and `OneToOne` relations without `targetEntity` (as generated by `make:entity`) are now drawn with their foreign key
- Only Doctrine-mapped properties are shown as columns (no more collections, relation objects or unmapped properties), including protected, readonly and constructor-promoted ones
- Table and column names, and column types, now follow Doctrine (`ORM\Table`, `ORM\Column`, `JoinColumn`, `createdAt` → `created_at`, `Types::*`, enums)
- Entities in sub-folders of `src/Entity`, legacy `@ORM` annotations and single-table / joined inheritance are now supported; enums, traits and interfaces are no longer drawn as tables
- Fields declared in traits, mapped superclasses and parent classes of `src/Entity` are now shown in the entity's table, as Doctrine maps them
- Bidirectional relations are drawn once, from the owning side
- The schema is now drawn outside a git repository too, and the git status of each column is correct in monorepos, for staged files and whatever the user's git configuration
- Security: entity file names are no longer passed to a shell (command injection through a crafted file name)
- No more freeze on very long entity files, and a fixed number of git calls instead of one per entity

**Viewers**
- Mermaid columns are written `type name` (they were swapped), with `PK` / `FK` markers
- Relations show their real cardinality (one-to-many, one-to-one, many-to-many)
- Odd names (reserved words, names starting with a digit, PHP class types, `constructor`...) no longer break the whole diagram
- Values such as `default('$')` or `</script>` in a migration no longer break the viewers
- The viewers follow the VS Code theme (light, dark, high contrast): the JSON viewer is readable in light themes
- Large schemas are drawn at a readable size and scroll inside the panel

**Extension**
- Running the command again refreshes the existing panel instead of opening a new one
- Clear error messages (unknown framework, missing `frameworkPath` folder, invalid `composer.json`), details and warnings in the new **DrawMeDatabase** output panel
- An empty schema shows a message instead of a blank diagram
- In multi-root workspaces, the folder of the active editor is used

### Changed
- Mermaid 10.9.8 is now bundled with the extension: diagrams work offline, with a strict Content Security Policy
- The extension activates once VS Code has started instead of at startup (`onStartupFinished`)
- The package is about 1 MB instead of 4.4 MB: `vsce` and `simple-git` are no longer shipped as runtime dependencies
- The JSON output no longer has the raw `additional` field, and relations now have a `type` (`many-to-one`, `one-to-one`, `many-to-many`)
- Development: Node 22+, `@vscode/vsce` 4, ESLint 9, unit tests (`npm run test:unit`) and an integration test (`npm test`)

### Known issues
- See the "Known limitations" section of the [README](README.md)

## [v1.2.0] - 2026-10-18

A new diagram viewer: Mermaid 12, zoom and pan, export, and the colors of your VS Code theme.

### Added
- **Zoom and pan**: drag the diagram to move it, Ctrl (Cmd on macOS) + mouse wheel or pinch to zoom, toolbar buttons to zoom in, zoom out, fit to window and show at 100 %, and keyboard shortcuts (`+`, `-`, `0`, `F`, arrows) when the diagram has the focus
- **Export**: save the diagram as SVG, PNG, Mermaid source (`.mmd`) or Markdown, copy the Mermaid source, and save or copy the JSON
- **Layout engines**: ELK (new default, compact with right-angled links, best for large schemas) or Dagre (the previous layout), and the direction of the diagram (top to bottom or left to right), from the toolbar or the new `DrawMeDatabase.layout` and `DrawMeDatabase.direction` settings
- A **Refresh** button in the toolbar and in the title bar of the panel, and the `DrawMeDatabase: Refresh Diagram` command
- The toolbar shows the framework, the project and the number of tables, and a link to the warnings
- The panel comes back after a reload of the window, with the same viewer and zoom

### Changed
- Mermaid 12.2.0 is bundled (instead of 10.9.8)
- The diagram uses the colors of the current VS Code theme (any theme, light, dark or high contrast)
- Attribute names keep their accents and non-Latin letters (`prénom`, `名前`), and nullable columns are shown as `type?`
- The diagram and JSON viewers are tabs of the same page: switching between them no longer reloads the panel, and refreshing keeps the zoom
- The JSON viewer is colored like code
- The commands are now `DrawMeDatabase: Draw Database Schema` and `DrawMeDatabase: Refresh Diagram`
- Errors of the diagram are written in the **DrawMeDatabase** output panel

## [v1.3.0] - 2026-10-18

### Added
- **Click on a table to open its code**: the migration that creates it (Laravel) or its entity class (Symfony) opens beside the diagram, at the right line. The tooltip of each table shows the file and the line
- **Search**: the "Filter tables" box of the toolbar (`Ctrl+F` / `Cmd+F`) keeps the tables whose name or one of whose columns contains the text, highlighted, with the tables they are linked to. `Escape` clears it. The JSON viewer and the exports follow the search
- **Automatic refresh**: the open diagram is drawn again when a migration or an entity is saved, created or deleted, and when `DrawMeDatabase.frameworkPath` changes. It does not bring the panel to the front, and keeps the previous diagram while the code cannot be read. The new `DrawMeDatabase.autoRefresh` setting turns it off
- The JSON output has the `source` (file and line) of each table, described with the rest of the format in `docs/pivot-format.md`

### Changed
- VS Code 1.96 is still the oldest supported version (`engines.vscode` stays `^1.96.0`): CI now runs the integration test, which draws the diagram in the real webview with the ELK and Dagre layouts, on VS Code 1.96.0 as well as on the latest version. Locally: `VSCODE_TEST_VERSION=1.96.0 npm test`

## [v1.4.0] - 2026-10-18

### Added
- **Live diagram**: the diagram follows what you type in a migration or an entity, before you save it (300 ms after you stop typing)
- **Git status in the diagram**, for Laravel and Symfony, in the colors of the git decorations of VS Code:
  - tables not in the last commit (new), changed since the last commit (modified), or changed in an editor and not saved yet (unsaved) get a colored outline and header
  - their uncommitted columns are marked `● new`, `● modified` or `● unsaved`
  - a legend counts the tables of each status, and the **Git** button of the toolbar (or the `DrawMeDatabase.showGitStatus` setting) hides or shows the status
- The diagram is refreshed after a commit, a checkout or a stage (through the built-in Git extension)
- The JSON output has the `git` status of each table, and of each column for Laravel too (it was Symfony only)

### Changed
- An automatic refresh that changes nothing is not drawn again, and while a large schema is being drawn, only the last edit is drawn next
- git runs only when files change on disk or in the repository, not while you type

## [v1.5.0] - 2026-10-18

### Added
- An API for other extensions (`docs/api.md`): the schema on screen and its changes, the parsers, exports added to the Export menu, focus on a set of tables, and the SVG of the diagram. DrawMeDatabase Pro is built on it
- The Export menu points to DrawMeDatabase Pro (SQL, DBML, TypeScript, documentation...) while it is not installed
- Parser options for tools: `columnSources` (where each column is declared) and, for Laravel, `until` (the schema right after a migration)
- The `marks` option of the diagram generator: a CSS class per table (`mark`) and a comment per column (`note`), for the tools of other extensions
- The `details` parser option: lengths, precisions, unsigned, default values, enum values, comments, auto-increments, indexes (unique, full text, spatial) and `ON DELETE` / `ON UPDATE` of the foreign keys, read from Laravel migrations and Doctrine entities (`docs/pivot-format.md`)

### Changed
- New animation in the README: the live diagram and its git status

## [v1.6.0] - 2026-10-18

### Added
- An options panel next to the diagram (the panel button of the toolbar): the options of the diagram, the appearance, the tools and exports of DrawMeDatabase Pro (greyed with a PRO badge until it is installed, locked when its trial has ended), the settings and the license
- Appearance: light or dark whatever the VS Code theme, seven palettes with a light and a dark version, custom colors (background, table headers, text, borders, links, highlight, git status), the font and the size of the text, the background grid

- What DrawMeDatabase Pro adds to the diagram, shown with a PRO badge in the free version: the git status of each column (setting `DrawMeDatabase.showColumnGitStatus`), the palettes, the custom colors and the fonts. The git status of the tables, the theme (auto, light, dark) and the text size stay free
- The schema time machine and the comparison with a database of DrawMeDatabase Pro in the tools of the options panel
- An inspector of the tables, in its own panel on the left: a click on a table shows its columns (keys, types, nullable, git status, and the line of each column), the tables it references and the ones that reference it, with buttons to open its file and to show its neighbours; a double-click (or Ctrl+click) opens its file. DrawMeDatabase Pro adds its indexes, defaults, history and actions
- French: the diagram, the messages, and the commands and settings in VS Code (`DrawMeDatabase.language`: `auto`, `en` or `fr`)
- API version 2: `registerTool()`, `connectPro()`, `registerTableInfoProvider()`, `getDisplaySettings()` and `onDidChangeDisplaySettings`, and the page scripts `i18n.js`, `appearance.js` and `sidepanel.js` for the panels of other extensions (`docs/api.md`)

### Fixed
- A column note or a git label holding two '~' (such as the comparisons of DrawMeDatabase Pro, `~ default: a~b`) no longer makes Mermaid reject the whole diagram, and a table name holding '~x~' is no longer drawn as '<x>': the first '~' is written as is, the next ones as the look-alike '∼'
- A ':' in a table name, a relation name or a column note (the comparisons of DrawMeDatabase Pro) is drawn as ':' instead of '&#58;', and a '#' as the fullwidth '＃' instead of '&#35;'

## [v1.8.0] - Unreleased

### Added
- Prisma: the tables of the Prisma schema (Prisma ORM 5 to 7), found where the Prisma CLI looks for it (`schema.prisma`, `prisma/schema.prisma`, the schema of `prisma.config.ts`, read without running it, or of the `prisma` section of `package.json`) or in a multi-file schema folder (`prisma/schema/`). PostgreSQL, MySQL, SQLite, SQL Server and CockroachDB
  - Models with their `@@map` / `@map` names and `@@schema`, the Prisma types (scalars, enums, `Unsupported("...")`), optional fields and scalar lists, primary keys (`@id`, `@@id`), unique columns, indexes (`@@index`, `@@unique`, `@@fulltext`), defaults and native types (`@db.*`) in the details
  - Relations from `@relation(fields, references)`: many-to-one or one-to-one (unique fields), composite and self relations, the join tables of the implicit many-to-many relations (`_AToB`, `_Name`), and the `onDelete` / `onUpdate` that `prisma migrate` writes
  - The live diagram, the git status of the tables and columns, the Schema view and the click on a table (the line of the model) work as for Laravel and Symfony, on every file of a multi-file schema. A model added to a schema file that is already committed is new, as in a new file, and an unsaved `prisma.config.ts` or `package.json` that moves the schema is followed live, with the edits of the new schema file
  - Only the `schema` of the config object of `prisma.config.ts` is read (not the `schema` option of a driver adapter), and Prisma 7 projects ignore `prisma.schema` of `package.json` as Prisma 7 does
  - A folder whose `package.json` only lists `prisma` or `@prisma/client` (the root of a monorepo whose schema is in a package) is not taken for a Prisma project: the message and the Schema view suggest setting `DrawMeDatabase.frameworkPath`
  - Views and composite types are skipped with a warning; a MongoDB schema draws nothing, with a warning
  - Checked against `prisma migrate diff` on real schemas (Cal.diy, Dub, Umami, Hoppscotch, Prisma's examples), kept as test fixtures
- Drizzle: the tables of the Drizzle ORM schema (drizzle-orm 0.x and 1.0), read from the schema files set in `drizzle.config.ts` (a file, a folder, a glob or a list; `.ts`, `.js`, `.mjs` or `.json`, read without running it) or at the usual locations (`src/db/schema.ts`, `src/schema.ts`, `db/schema.ts`, `drizzle/schema.ts`, a schema folder), following their imports and re-exports (relative paths, the path aliases of `tsconfig.json`). The TypeScript of the project is never run. PostgreSQL, MySQL, SQLite (and Turso) and SingleStore
  - The tables drizzle-kit creates: the exported `pgTable()`, `mysqlTable()`, `sqliteTable()` and `singlestoreTable()`, `pgSchema().table()`, the table creators and their prefix, `snakeCase.table()` and `camelCase.table()` of drizzle-orm 1.0; the columns with their name (the first argument, else the key with the `casing` of `drizzle.config.ts`), builder, `.notNull()`, `.primaryKey()`, serial and identity columns, arrays, enums (`pgEnum`, `mysqlEnum`), custom types
  - Columns written as an object or in a callback (`(t) => ({ ... })`), spread from an object or a function of the same file or of an imported one (`...timestamps`), made by a helper of the project; a spread that cannot be read is told in the output
  - Relations from `.references()` and `foreignKey()` (many-to-one or one-to-one, composite, self and circular references), with their `onDelete` / `onUpdate`; `relations()` and `defineRelations()` are not foreign keys and are not drawn
  - Primary keys, unique columns, indexes (`index()`, `uniqueIndex()`, `unique()`, an SQL expression as written), defaults (`.default()`, ``sql`...` ``, `defaultNow()`, `defaultRandom()`), lengths, precision and scale, unsigned and auto-increment columns in the details
  - The live diagram, the git status of the tables and columns, the Schema view and the click on a table (the line of its variable) work as for the other frameworks, on every schema file and the files the columns are spread from. A table added to a committed file is new, as in a new file
  - As drizzle-kit, the tables that are not exported, the views and the tables of another MySQL database (`mysqlSchema()`) are skipped, with a warning
  - Checked against drizzle-kit 0.31 (`drizzle-kit generate`) and 1.0.0-rc.4 on real schemas (create-t3-app, Next.js SaaS Starter, Vercel's Chatbot, Cap, OpenStatus, Midday) and hand-made ones, kept as test fixtures
- SQL: the schema built by replaying the SQL migrations of a project in the order of their tool, or by reading a dump of the schema, without a database. PostgreSQL first, with the basics of MySQL and SQLite. The SQL is read, never run
  - Supabase (`supabase/migrations`), Flyway (`V<version>__<name>.sql`, by version, in sub-folders too, each folder once even through symbolic links; repeatable migrations left out), dbmate (the `-- migrate:up` section), golang-migrate (`*.up.sql`, by version number), goose (`-- +goose Up`, `StatementBegin`), diesel, numbered migrations (sqlx, Atlas...), Rails `db/structure.sql`, a dump at the root or in `db/` (`schema.sql`, `structure.sql`, `dump.sql`...); the output of `prisma migrate` and drizzle-kit (in the order of its journal) when the project has no Prisma or Drizzle schema; the migrations in the framework folder itself, and any `.sql` file of it when `DrawMeDatabase.framework` is `sql`
  - `CREATE TABLE` (types, lengths and precisions, `NOT NULL`, defaults, primary keys, `UNIQUE`, foreign keys with `ON DELETE` / `ON UPDATE`; `CHECK` ignored), `CREATE TYPE ... AS ENUM` and `ALTER TYPE`, `CREATE [UNIQUE] INDEX` (partial, expressions), `ALTER TABLE` (`ADD` / `DROP` / `ALTER` / `RENAME COLUMN`, `ADD` / `DROP CONSTRAINT` by their name or the one PostgreSQL gives them, `RENAME TO`, `SET SCHEMA`, the keys of `supabase db diff`), `DROP TABLE`, `DROP SCHEMA ... CASCADE`, schema-qualified and quoted names (unquoted ones folded to lower case on PostgreSQL), the search path, comments, dollar-quoted bodies, the DDL of `DO` blocks, transactions, `COPY ... FROM stdin` data. Functions, triggers, policies, grants, extensions, views and data are skipped without breaking the replay; a statement that could change tables and is not understood is named in the output
  - MySQL: backticks, `AUTO_INCREMENT`, table options (`ENGINE=...`), inline `KEY` / `INDEX` / `UNIQUE KEY` / `FULLTEXT KEY` / `CONSTRAINT`, `enum` and `set` values, unsigned, `ON UPDATE CURRENT_TIMESTAMP`, `MODIFY`, `CHANGE`, `FIRST` / `AFTER`, `RENAME TABLE`, `DELIMITER` and the executable comments of mysqldump. SQLite: `AUTOINCREMENT`, `WITHOUT ROWID`, untyped columns, triggers, the tables rebuilt by prisma migrate and drizzle-kit, libSQL's `ALTER COLUMN ... TO`
  - A click on a table opens its `CREATE TABLE`, a click on a column the statement that declared it or the last migration that changed it; the git status of the tables and columns follows the migrations, and a table added to a committed dump is new. The live diagram, the Schema view and the `until` option (the schema right after a migration, for the time machine of DrawMeDatabase Pro) work as for Laravel
  - Detected with a lower score than the frameworks (45 for the migrations of a tool, 40 for a dump): a Laravel, Prisma or Drizzle project is drawn with its framework, `DrawMeDatabase.framework` set to `sql` draws its SQL
  - Checked against PostgreSQL 17, MySQL 8.4 and SQLite on real migrations and dumps (Chatbot UI, Basejump, Next.js Subscription Payments, Harness, OpenFGA, Umami, OpenStatus, Atala PRISM, Feedbin, Pagila, listmonk, Sakila, GitLab) and hand-made ones, kept as test fixtures: the same tables, columns, keys, foreign keys and indexes as the database
- Laravel: the schema dump of `php artisan schema:dump` (`database/schema/<connection>-schema.sql` or `.dump`, MySQL, PostgreSQL or SQLite) is loaded first, then the migrations it does not list, as `php artisan migrate` does on a new database: a project whose old migrations were pruned is drawn whole. The dump of the default connection is read (`DB_CONNECTION` of `.env`, else `config/database.php`); its file is a source of the live refresh and of the git status, and the Schema view and the inspector offer to open the SQL file (not a migration) for the tables it creates
- Pluggable parsers: each framework is a parser module with an id, a label, a detection score, the files it reads (`sources()`) and its `parse()`, listed in `parsers/registry.js` (`docs/parsers.md`). The file watcher, the live refresh of the unsaved editors and the git status follow the files each parser declares, instead of the PHP files of two fixed folders. When a parser cannot read a file it needs for the detection (an invalid `composer.json`) while another one recognizes the folder, its error is a warning in the output
- `DrawMeDatabase.framework` setting: `auto` (the default) detects the framework, `laravel`, `symfony`, `prisma`, `drizzle` or `sql` chooses it for a project that matches several of them. The output lists the frameworks found, with their score
- API version 3 (`docs/api.md`): `getFrameworks()` (the supported stacks, `{ id, label }`), `getSources(basePath, framework)` (what a parser reads), and an `options.framework` for `detectFramework()`
- The `nativeType` detail of the columns (`docs/pivot-format.md`): the native type declared for the database (Prisma `@db.VarChar(255)` gives `VarChar(255)`)

### Changed
- The messages and the Schema view no longer name Laravel and Symfony only: the message of a folder without a supported project lists the supported frameworks, and the output names the files read when no table is found
- The Markdown export names the framework from the label given by the extension
- The description and the keywords of the extension name the supported stacks

Laravel and Symfony projects are read as before: same tables, warnings and git status (except the Laravel projects that have a schema dump, now read), and Laravel still wins when a project is both. Laravel and Symfony also win a tie with Prisma (a PHP project with a Prisma schema), and Prisma wins a tie with Drizzle (a project moving from one to the other); `DrawMeDatabase.framework` chooses the other one there. Every framework wins over SQL.
